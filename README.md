# Мост «GitHub (приватный репо) ↔ Vercel ↔ Пользователь»

Система для хранения и выдачи лицензионных ключей, у которой:

- **Данные** (`database.json`) лежат в вашем **приватном** репозитории GitHub.
- **Vercel** — единственный, кто имеет токен доступа к репозиторию. Он выступает
  мостом: пользователь и его JavaScript никогда не видят GitHub-токен и не
  обращаются к GitHub напрямую.
- **Публичный эндпоинт** `/api/validate` — им пользуется ваше приложение/скрипт
  у клиента, чтобы проверить ключ. Отдаёт только `valid: true/false` и минимум
  метаданных — никогда не отдаёт всю базу.
- **Админ-эндпоинты** `/api/admin/*` защищены отдельным секретом `ADMIN_TOKEN`
  и дают полный CRUD: добавить, изменить, удалить, забанить/разбанить,
  задать срок действия, лимит использований, заметки.
- **WebUI администратора** — `public/admin/index.html`, открывается по адресу
  `https://ваш-проект.vercel.app/admin`.

## Структура

```
api/
  validate.js              # публичная проверка ключа (для внешних приложений)
  app-content.js             # проверяет ключ и ТОЛЬКО тогда отдаёт HTML защищённого приложения
  lib/github.js               # вся работа с GitHub Contents API (токен только тут)
  lib/license.js               # общая логика проверки статуса ключа
  lib/auth.js                   # проверка ADMIN_TOKEN
  admin/
    keys.js                      # GET (список) / POST (создать)
    keys/[key].js                 # PUT (изменить) / DELETE (удалить)
    keys/[key]/ban.js              # POST { ban: true|false }
public/
  index.html                # публичный "шлюз" — форма ввода ключа, БЕЗ кода приложения
  admin/index.html          # панель администратора
app-content/
  teacher-planner.html      # реальный код защищённого приложения — НЕ в /public,
                              # своего URL не имеет, отдаётся только через api/app-content.js
database.example.json       # пример структуры базы — положите как database.json в приватный репо
```

## Как код приложения защищён от выдачи без ключа

Важно понимать разницу между двумя подходами:

- **Плохо (только визуально):** весь код лежит в публичном HTML-файле, JavaScript просто
  прячет интерфейс, пока не введён ключ. Код при этом всё равно скачан в браузер —
  любой может открыть «Просмотр кода страницы» и забрать его, даже без ключа.
- **Как сделано здесь:** файл `app-content/teacher-planner.html` лежит **вне** папки
  `public/` — у него нет собственного URL, Vercel не отдаёт его напрямую никому.
  Публично доступна только крошечная страница `public/index.html` — форма ввода
  ключа, в ней нет кода самого приложения.

Поток запроса:

1. Пользователь открывает `https://ваш-проект.vercel.app/` — видит только форму
   ввода ключа (~5 КБ, никакой логики приложения там нет).
2. Вводит ключ → браузер отправляет `POST /api/app-content { key, consumeUse: true }`.
3. Сервер (Vercel) проверяет ключ в `database.json` в приватном репозитории.
   Только если ключ действителен, сервер читает `app-content/teacher-planner.html`
   с диска и отдаёт его содержимое в ответе.
4. Браузер получает HTML и полностью заменяет им текущую страницу
   (`document.write`) — только теперь, после успешной проверки, в браузере
   оказывается код приложения.
5. Ключ сохраняется в `localStorage` на этом устройстве. При следующих визитах
   `index.html` автоматически (без ввода) шлёт `POST { key, consumeUse: false }` —
   тихая повторная проверка без списания использования. Если ключ забанили или
   он истёк — пользователя вернёт на форму ввода с объяснением причины.

**Честная оговорка:** это защищает от случайного скачивания/расшаривания кода
человеком без ключа и от индексации/копирования исходника через простой просмотр
страницы. Но человек, у которого ключ **есть**, технически может открыть
инструменты разработчика после успешной активации и сохранить полученный ответ
сервера — от копирования кода легитимным пользователем ни один чисто клиентский
метод защитить не может в принципе (код всё равно должен выполняться в его
браузере). Это защита уровня «не отдавать код всем подряд», а не DRM.

## 1. Подготовка приватного репозитория

1. В приватном репозитории создайте файл `database.json` со структурой:

   ```json
   { "keys": [] }
   ```

   (см. `database.example.json` для примера с одним ключом).

2. Создайте **fine-grained Personal Access Token** на GitHub
   (Settings → Developer settings → Fine-grained tokens):
   - Repository access: **только этот репозиторий**.
   - Permissions → Contents: **Read and write**.
   - Больше никаких прав токену не давайте.

## 2. Переменные окружения на Vercel

В настройках проекта на Vercel (Project → Settings → Environment Variables)
добавьте (см. `.env.example`):

| Переменная | Значение |
|---|---|
| `GITHUB_TOKEN` | токен из шага выше |
| `GITHUB_OWNER` | ваш логин/организация на GitHub |
| `GITHUB_REPO` | название приватного репозитория |
| `GITHUB_FILE_PATH` | `database.json` (или путь, если файл в подпапке) |
| `GITHUB_BRANCH` | `main` (или ваша ветка) |
| `ADMIN_TOKEN` | длинный случайный секрет для входа в админку (`openssl rand -hex 32`) |

**Не коммитьте `.env` с реальными значениями** — на Vercel их добавляют через
UI или `vercel env add`.

## 3. Деплой

Вариант А — через Vercel CLI:

```bash
npm i -g vercel
cd license-system
vercel        # первый деплой, свяжет проект
vercel --prod
```

Вариант Б — через GitHub-интеграцию Vercel: закиньте эту папку в **отдельный**
репозиторий (публичный или приватный — не важно, это уже не хранит ключи,
только код) и подключите его в Vercel как проект. Переменные окружения
всё равно задаются в Vercel, а не в этом репозитории с кодом.

> Важно не перепутать: репозиторий с **кодом моста** (эта папка) и репозиторий
> с **database.json** — это два разных репозитория. Код можно публиковать
> открыто (в нём нет секретов, они только в Vercel env vars), а вот
> `database.json` должен оставаться в приватном репозитории.

## 4. Использование

### Проверка ключа из вашего приложения (клиент)

```js
const res = await fetch("https://ваш-проект.vercel.app/api/validate", {
  method: "POST",
  headers: { "Content-Type": "application/json" },
  body: JSON.stringify({ key: "AB12-CD34-EF56-7890", consumeUse: true }),
});
const data = await res.json();
// { valid: true, remainingUses: 4, expiresAt: null }
// или { valid: false, reason: "banned" | "expired" | "not_found" | "max_uses_reached" | "disabled" }
```

`consumeUse: true` — засчитывает использование (инкрементирует `uses` и пишет
коммит в репозиторий). Если вам нужна просто проверка без списания —
не передавайте это поле или передайте `false`.

### Админ-панель

Откройте `https://ваш-проект.vercel.app/admin`, введите `ADMIN_TOKEN` —
и управляйте ключами: добавление, редактирование, срок действия, лимит
использований, бан/разбан, удаление, заметки. Токен хранится только в
`sessionStorage` этой вкладки (пропадает при закрытии вкладки).

## Ограничения и что стоит знать

- **Гонки записи**: если два запроса одновременно пишут в `database.json`,
  GitHub вернёт конфликт версий (409) — код автоматически перечитывает файл
  и повторяет попытку (до 3 раз). Для нагрузки в духе «десятки проверок в
  секунду» этого достаточно; для действительно высокой нагрузки GitHub API
  как база данных — не лучший выбор (стоит смотреть на Vercel KV/Postgres).
- **Rate limits GitHub API**: обычный токен — 5000 запросов/час, для
  большинства сценариев с лицензионными ключами этого с запасом хватает.
- **ADMIN_TOKEN** — единственная защита админки. Храните его как пароль,
  используйте `openssl rand -hex 32`, не отправляйте по незащищённым каналам.
- Каждое изменение ключа создаёт коммит в приватном репозитории — это даёт
  бесплатную историю изменений (можно посмотреть кто/когда менял ключ через
  `git log database.json` в репозитории).
